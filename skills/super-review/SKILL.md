# Super Review — 深度代码审查

## 核心原则

### 原则一：绝对禁止泛泛总结

以下表述**一律禁止出现**。这些话没有指出任何具体问题，对代码改进毫无帮助：

| 禁止表述 | 为什么是废话 |
|----------|------------|
| "整体实现清晰，结构合理" | 没有指出任何具体问题或改进点 |
| "可以考虑继续优化可读性" | 没有说哪里可读性差、为什么差、怎么改 |
| "功能完整，建议加强错误处理" | 没有指出哪里缺错误处理、缺什么处理、什么条件下会出问题 |
| "逻辑基本正确，注意边界情况" | 没有指出哪个边界、什么输入下会越界 |
| "代码质量不错，有一些小细节可以优化" | 既没说明"不错"在哪，也没说明"小细节"是什么 |

**每条审查意见必须六要素齐全：**

1. **文件路径** — 哪个文件
2. **行号或函数** — 精确位置
3. **触发条件** — 什么输入/操作/状态下会触发
4. **问题原因** — 为什么这是个问题
5. **影响范围** — 对用户或系统有什么后果
6. **最小修复建议** — 具体怎么改，能一行修完不写两行

### 原则二：先报告，后修复

执行的顺序不可颠倒：

1. 只读 Diff，分析改动
2. 输出 Markdown 审查报告
3. **等待用户确认**（用户说"可以修复""按报告改"等明确指令）
4. 用户确认后才开始修改代码
5. 绝对禁止在生成报告之前修改任何文件

### 原则三：风险分级

| 等级 | 含义 | 判断标准 | 响应 |
|------|------|---------|------|
| **P0** | 紧急 | 功能不可用 / 数据丢失 / 安全漏洞 / 用户流程完全阻断 | 必须立即修复 |
| **P1** | 高 | 功能异常 / 错误结果 / 严重影响用户体验 | 应该在本轮修复 |
| **P2** | 低 | 代码质量问题 / 潜在风险 / 轻微体验瑕疵 | 可选修复 |
| **No issues** | 无问题 | 所有审查点均满足要求 | 无需修复 |

### 原则四：最小化修复

- 只修复审查报告中明确指出的问题
- 不做"顺带优化"——不碰任何与问题无关的代码
- 不改动审查范围之外的文件
- 能一行修完绝不写两行

### 原则五：修复后必须再次验证

- 每修复一个问题，立即验证该问题是否真正解决
- 确认修复没有引入新的 P0/P1 风险
- 运行已有测试确保不回归
- 输出验证结果

## 审查流程

### 第一步：Diff 分析（永远的第一步）

**在审查任何代码之前，必须先做 Diff 分析。跳过这一步直接开始审查是违规的。**

只读改动，不修改任何文件。必须回答以下四个问题，写入审查报告：

#### Q1：涉及哪些文件？

列出本次 Diff 中所有新增、修改、删除的文件，按目录分组：

```
src/
  ├── services/payment.ts      (修改，+42 -15)
  ├── hooks/useAuth.ts         (修改，+8 -3)
  └── utils/validator.ts       (新增)
tests/
  └── services/payment.test.ts (新增)
```

#### Q2：哪些改动和任务直接相关？

逐文件说明每个改动对应什么需求或修复。如果无法确定某个改动与任务的关联，标注出来。

#### Q3：有没有无关改动？

识别不属于当前任务范围的改动。以下情况需要特别关注：

- 仅格式化变更（空格、换行、缩进）
- 只改了注释
- 与需求描述明显不符的文件修改
- 引入新依赖但需求里没提到

如果存在无关改动，需要在报告中标注并说明是否需要移除。

#### Q4：准备重点审查哪些流程？

根据 Diff 内容和任务目标，明确列出本次审查的重点流程。例如：

- "支付回调处理流程：重点审查数据流完整性 + 安全签名校验"
- "用户注册表单提交流程：重点审查异常流（网络失败、重复提交）+ 用户体验（验证反馈）"

### 第二步：按五类风险逐项审查

对每个文件、每个改动点，按以下五类风险逐一排查。不是每一类都必须有问题，但每一类都必须检查到。

#### 1. 数据流

检查数据在系统中的传递、转换和状态管理：

- 数据传递路径是否完整（从哪里来，到哪里去）
- 类型转换是否正确（`string` → `number`、`null` → `undefined` 等边界）
- 状态更新是否一致（多处持有的同一份数据是否同步）
- 有没有使用未初始化的数据
- Props/参数传递是否正确（必传参数是否缺失、类型是否匹配）
- 异步数据到达前 UI 渲染是否使用了空值

#### 2. 异常流

检查错误处理和边界条件：

- 有没有被静默吞掉的异常（空的 catch 块）
- 网络请求失败的处理（超时、5xx、断网）
- `null` / `undefined` / 空字符串 / 空数组 / 空对象的处理
- 外部依赖不可用时的降级行为（第三方 API、数据库连接）
- 并发/竞态条件（快速连续点击、请求返回顺序）
- 资源清理（组件卸载时是否取消订阅、清除定时器）

#### 3. 用户体验

检查交互逻辑和界面反馈：

- 用户操作是否有即时反馈（加载态、成功/失败提示）
- 表单验证反馈是否及时、清晰（错误信息指明修复方式）
- 页面/组件的状态完整性（空状态、错误状态、加载状态、正常状态）
- 交互流程是否符合用户心理模型（返回键、取消操作、确认弹窗）
- UI 一致性（样式、间距、颜色、命名是否遵循现有规范）

#### 4. 测试缺口

检查测试覆盖情况：

- 新增功能/组件是否有对应测试
- 边界条件有没有测试（空输入、极值、特殊字符）
- 异常路径有没有测试（网络失败、数据为空、权限不足）
- 测试是否验证了有意义的断言（不是"渲染不出错"就算通过）
- 测试命名是否清晰描述了测试场景

#### 5. 安全隐私

检查安全相关风险：

- 用户输入是否经过校验和消毒（XSS、SQL 注入）
- 有没有硬编码的密钥、Token、密码、API Key
- 权限检查是否完整（前端+后端双重检查）
- 敏感数据是否暴露（日志、错误消息、URL 参数、响应体）
- 传输安全（敏感接口是否强制 HTTPS）
- 第三方依赖是否有已知漏洞

### 第三步：输出审查报告

将审查结果整理为 Markdown 格式报告。**必须使用以下模板结构：**

```markdown

- **审查范围**：[本次审查的功能或模块]
- **审查依据**：[Commit SHA 或 PR 编号或 Diff 来源]
- **审查日期**：[YYYY-MM-DD]
- **综合风险等级**：[P0 / P1 / P2 / No issues]

---

## 一、Diff 分析

### Q1：涉及哪些文件？

[按目录分组列出所有文件]

### Q2：哪些改动和任务直接相关？

### P0 — 紧急

> 如果此等级没有发现问题，写"无"。

#### [P0-N] 问题标题

- **文件**：`[文件路径]` 第 [行号] 行 `[函数名]` 函数
- **触发条件**：[什么输入/操作/状态下会触发]
- **问题原因**：[为什么这是个问题]
- **影响范围**：[对用户或系统的具体后果]
- **修复建议**：[最小化修改方案，可执行的步骤]

> 如果此等级没有发现问题，写"无"。

## 三、审查检查清单

### 数据流
- [x] [通过项]
- [ ] **← 发现问题**：[风险编号] 简要说明

- [ ] **← 发现问题**：[风险编号] 简要说明

```

### 第四步：等待人工确认

审查报告输出后，**必须停止，等待用户指示**：

1. 用户可能需要补充说明、要求重新审查某个点
2. 用户可能调整风险等级
3. 用户在确认报告后给出修复指令（"可以修复了""按报告改""先修 P0 和 P1"等）

**在用户明确给修复指令之前，不得修改任何代码。**

### 第五步：最小化修复

收到修复指令后，按以下规则执行：

1. **按风险等级顺序修复**：P0 → P1 → P2
2. **严格按照修复建议实施**，不自由发挥
3. **只修改审查报告中列出的文件和行**
4. **每修复一个问题，立即验证**
5. **禁止顺带优化**——不修改审查范围外的代码

### 第六步：修复验证

修复完成后输出验证结果：

```markdown

- [x] **已修复**：[简述实际的修改]
- [x] **验证通过**：[如何验证问题已解决]
- [x] **无新问题**：已有测试全部通过 / 手动验证无回归

### [P1-1] 问题标题
- [x] **已修复**：[简述实际的修改]
- [x] **验证通过**：[如何验证问题已解决]
- [x] **无新问题**：已有测试全部通过 / 手动验证无回归
```

## No Issues 处理规范

如果审查后真的**没有任何问题**，不可敷衍了事。

### 正确做法

写明 "**No issues**"，然后列出实际检查了哪些具体点：

```markdown
No issues。本次审查覆盖以下检查点：

- 数据流：注册表单数据从组件→状态管理→API请求→数据库写入的完整链路，包含类型转换和字段映射
- 异常流：密码加密失败、数据库写入失败、邮箱重复注册三条异常路径，均有对应的错误处理
- 用户体验：空表单提交提示、密码格式校验实时反馈、提交成功跳转、提交失败重试按钮——四种交互状态完整
- 测试缺口：注册 API 的成功/失败场景均有集成测试覆盖，前端表单组件有单元测试覆盖校验逻辑
- 安全隐私：密码使用 bcrypt 加盐加密入库，邮箱输入做格式校验，无硬编码密钥
```

### 错误做法

```markdown
No issues。整体质量不错。
```

**错误原因**：没有列出任何具体的检查点。无法判断审查是否真正覆盖了五类风险，还是走马观花。

```markdown
No issues。代码写得很好，没有明显问题。
```

**错误原因**：同上。"写得很好"和"没有问题"都是空话——到底检查了什么？

## 正反示例

### 示例 1：泛泛总结 vs 具体问题

#### ❌ 反例

```
这段代码整体不错，结构思路清晰，逻辑完整。可以考虑优化一下可读性。
```

**为什么错**：没有指出任何一个具体问题。"优化可读性"是空话——哪里可读性差？怎么优化？为什么需要优化？

#### ✅ 正例

```
src/hooks/useAuth.ts 第 23 行 fetchUserProfile 函数：
触发条件：网络请求失败时（超时或返回 5xx）
问题原因：try-catch 的 catch 块为空，异常被静默吞掉
影响范围：用户登录后资料加载失败时页面白屏，无错误提示
修复建议：在 catch 块中调用 setError({ type: 'profile', message: '用户资料加载失败，请刷新重试' })，
并将其渲染到页面对应的 ErrorBoundary 区域
```

---

### 示例 2：模糊建议 vs 可执行建议

#### ❌ 反例

```
建议增加错误处理。
```

**为什么错**：没有说在哪里加、加什么类型、怎么加、为什么需要。

#### ✅ 正例

```
src/components/LoginForm.tsx 第 45 行 handleSubmit 函数：
触发条件：API 返回非 2xx 状态码时
问题原因：只处理了 200 响应，401（密码错误）、429（频率限制）、5xx（服务端错误）均未处理
影响范围：密码错误时页面无提示，用户无法知道为什么登录失败
修复建议：
  1. 在 handleSubmit 的 response 处理中增加状态码判断
  2. 401 → setError('邮箱或密码错误')
  3. 429 → setError('尝试次数过多，请 5 分钟后再试')
  4. 5xx → setError('服务异常，请稍后重试')
```

### 示例 3：敷衍的 No Issues vs 可验证的 No Issues

#### ❌ 反例

```
没有发现问题，代码质量较高。
```

**为什么错**：无法判断审查是否完整。可能根本没仔细看。

#### ✅ 正例

```
No issues。本次审查覆盖以下检查点：

- 数据流：密码重置流程的完整数据链路——用户输入邮箱 → API 生成令牌 → 邮件服务发送 → 用户点击链接 → 令牌校验 → 密码更新，每个环节的数据传递均有校验
- 异常流：令牌过期、令牌不存在、邮箱格式错误、新密码与旧密码相同、数据库写入失败——五种异常路径均被处理
- 用户体验：发送邮件时显示加载态、成功发送提示（含邮箱掩码）、令牌过期提示含重新发送入口、新密码强度实时提示
- 测试缺口：以上异常路径均有集成测试覆盖，前端密码强度校验有单元测试
- 安全隐私：重置令牌使用 crypto.randomUUID 生成，60 分钟过期，一次性使用后失效；邮件中不含明文令牌，仅含链接
```

## 执行规则

### 规则一：Diff 优先

进入审查后，**第一步永远是 Diff 分析**。在完成 Q1-Q4 四个问题的回答之前，绝对禁止修改任何代码。

### 规则二：逐级报告

按 P0 → P1 → P2 → No issues 的顺序组织报告。先呈现最严重的问题，让读者一眼看到最重要的结论。

### 规则三：一条意见一个问题

每条风险发现是独立的条目，不能把多个问题合并成一条。如果一个文件有 3 个问题，拆成 3 条。

### 规则四：P0/P1 必须带修复建议

P0 和 P1 级别的问题强制附带可执行的修复建议。P2 建议附带，但非强制。

### 规则五：修复后回归

所有修复完成后必须进行回归验证：
- 确认问题已解决
- 确认未引入新问题
- 输出验证结果

### 规则六：尊重项目现有规范

审查时以项目的现有规范和架构为基准，而不是个人偏好：

- 项目用 `camelCase` 就不要建议改成 `snake_case`
- 项目有统一的错误处理中间件，新代码应遵循而不是另写一套
- 项目的目录结构和模块划分约定优先于"常见最佳实践"

### 规则七：不确定的问题标注出来

如果某个问题无法确定是否为真问题（例如需要更多上下文），标注为"待确认"，不要强行归类为 P0/P1/P2：

```markdown
#### [待确认] 可能的数据竞争

- **文件**：`src/hooks/useOrderPolling.ts` 第 34 行
- **触发条件**：用户快速重复点击"刷新"按钮时，可能触发多个轮询循环
- **状态**：需要确认 `startPolling` 调用方是否有防重复点击处理
```

## 触发场景

以下场景应调用本技能：

| 用户输入 | 场景 |
|---------|------|
| "帮我 Review 一下代码"、"审查代码"、"Code Review" | 通用代码审查 |
| "Review this PR"、"看看这个 PR" | PR 审查 |
| "帮我看看有没有安全问题"、"安全审查" | 安全专项审查 |
| "合并前帮我检查一下" | 合并前质量检查 |
| "看看这段代码有没有 bug"、"检查代码质量" | 质量审查 |

以下场景**不触发**本技能：

| 用户输入 | 原因 | 应使用的技能 |
|---------|------|------------|
| "帮我修一下这个 bug" | 直接修复，不需要审查报告 | 无，直接修复 |
| "这段代码怎么优化性能" | 性能优化建议 | 无，直接分析 |
| "帮我写一个功能" | 新功能开发 | 无，直接实现 |
| "这段代码是干什么的" | 代码解释 | 无，直接解释 |
