## 命名规范

### 文件与目录

| 类型 | 命名规则 | 示例 |
|------|----------|------|
| 目录 | （如 kebab-case） | `user-profile/` |
| 组件文件 | （如 PascalCase） | `UserProfile.tsx` |
| 工具文件 | （如 camelCase） | `formatDate.ts` |
| 常量文件 | （如 UPPER_CASE） | `API_CONFIG.ts` |
| 测试文件 | （与源文件同名 + .test） | `formatDate.test.ts` |

### 代码标识符

| 类型 | 命名规则 | 示例 |
|------|----------|------|
| 变量 / 函数 | camelCase | `userName`, `getUserById()` |
| 类 / 接口 | PascalCase | `UserService`, `IUser` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 私有属性 | （如 _ 前缀 或 # 前缀） | `_internalState` |

## 目录结构约定

```
src/
├── components/      # 可复用 UI 组件
├── pages/           # 页面级组件
├── services/        # 业务逻辑层
├── utils/           # 通用工具函数
├── hooks/           # 自定义 hooks
├── types/           # 类型定义
├── config/          # 配置文件
└── assets/          # 静态资源
```

## 模块化原则

### 文件规模

- 单个文件不超过 500 行
- 单个函数不超过 50 行（特殊情况除外）
- 单个组件职责单一

### 模块解耦

- 模块间通过接口通信，不直接依赖具体实现
- 避免循环依赖
- 共享代码抽取到公共模块

### 导入顺序

1. 外部依赖
2. 内部模块（按层级从远到近）
3. 相对路径导入

## 注释规范

### 必须加注释的情况

- 非显而易见的设计决策（为什么这样做而不是那样做）
- 绕过已知 bug 或框架限制的 workaround
- 复杂的算法或业务逻辑
- 公开 API 或导出函数

### 不必要加注释的情况

- 代码本身已经能清楚表达的意图
- 显而易见的操作

## 错误处理

- 不要吞掉异常，至少记录日志
- 在系统边界（API 入口、数据库调用、外部服务调用）统一处理错误
- 用户可见的错误信息应友好且不含技术细节

## 测试规范

- 测试文件放在源文件同目录或 `__tests__/` 目录下
- 测试文件命名：`<源文件名>.test.<扩展名>`
- 关键业务逻辑必须覆盖
- 公共工具函数必须有单元测试

## 代码审查要点

- [ ] 命名是否清晰、符合规范
- [ ] 是否有重复代码可以抽取
- [ ] 是否有潜在的性能问题
- [ ] 错误处理是否完善
- [ ] 是否有安全风险（参考 SECURITY.md）
- [ ] 是否符合架构约定（参考 ARCHITECTURE.md）
