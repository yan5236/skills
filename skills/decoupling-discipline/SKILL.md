# 架构解耦纪律 (Decoupling Discipline)

## 一、你必须理解的危机：屎山如何长成

**复杂度不是线性增长的。** 假设项目有 n 个部分，如果它们互相耦合，各部分之间的关系会接近平方级增长（O(n²)）。这意味着：

- 代码量翻一倍 → 复杂度可能翻四倍
- 代码量翻十倍 → 复杂度可能翻一百倍

**你的理解能力是线性的。** 你能写、能读、能改的代码量有上限，但屎山是平方级膨胀的。这两条曲线一旦赛跑，结局是注定的——迟早有一天你被自己写的屎山彻底淹没。修改一行代码需要同时理解十个文件，修好一个 bug 制造两个新 bug。

**唯一解法：拆。** 把一个大屎山拆成 k 个独立的小屎山。每个小屎山的内部复杂度是 O((n/k)²)，k 个加起来是 O(n²/k)。k 越大，总复杂度越低。

**但你不能无限拆。** 每拆出一个模块就多一个接口。接口有成本——定义、维护、调用、调试，这个成本随模块数量增长。架构师的核心能力就是找到 **"耦合成本 + 接口成本"的最小值**，即复杂度最优平衡点。

> 这不是理论问题。n 超过几千行后，不做解耦的项目必然走向"改一行崩三处"的结局。Windows 系统有数亿行代码却没崩成屎山，靠的就是这一套解耦架构。

## 二、五项结构性戒律

以下五条戒律不是"最佳实践建议"，而是**结构性命令**。违反任何一条都会让屎山加速膨胀。

---

### 戒律一：依赖接口而非实现 (Contract Over Concrete)

**为什么重要**：当模块 A 直接依赖模块 B 的具体实现时，B 的任何内部改动都会级联破坏 A。解耦的第一步就是切断这条链路——A 只认知 B 的接口，不知道也不关心 B 内部怎么实现。

**规则**：
- 模块之间的通信必须通过接口、抽象类、协议或 API 签名
- 绝不直接 import/require 对方模块的具体实现类
- 接口必须稳定：不随实现细节变动

**编码时检查**（每一项都必须在编码前确认）：
- [ ] 模块 A 是否直接引用了模块 B 的具体实现类（而非接口）？是 → **违规，立即修正**
- [ ] 能否在不修改调用方的情况下替换被调用方的实现？否 → **接口设计不合格**
- [ ] 被调用方的接口是否暴露了实现细节（如具体数据库类型、第三方SDK名称）？是 → **抽象层次不够**

**正例 vs 反例**：

```typescript
// ❌ 反例：直接依赖实现
import { UserService } from './services/userService'
const users = await userService.queryAll()

// ✅ 正例：依赖接口
import { IUserRepository } from './types'
// 调用方只认知接口，不关心是 MySQL 还是 MongoDB 实现
const users = await userRepo.queryAll()

// ❌ 反例：接口暴露实现细节
interface IPaymentService {
  chargeViaStripe(amount: number, token: string): Promise<StripeResult>
}

// ✅ 正例：接口抽象实现
interface IPaymentService {
  charge(amount: number, paymentMethod: PaymentMethod): Promise<ChargeResult>
}
```

### 戒律二：单一职责模块化 (One Job, One Module)

**为什么重要**：一个模块做多件事 = 多处修改都会动到它 = 耦合放大器。判断标准极其简单：**能不能用一句话说清楚这个模块做什么**。如果需要说"和"、"以及"、"同时",它就已经偷偷长成大屎山了。

**规则**：
- 每个模块/文件/类只做一件事，且这件事能用一句话命名
- 模块名必须精确描述其职责（`utils`、`helpers`、`common` 是垃圾桶，禁止）
- 两个不相关的函数绝不出现在同一文件中

**编码时检查**：
- [ ] 能否用一句话（不含"和"、"以及"、"同时"）描述这个模块？否 → **拆分**
- [ ] 模块名是否精确描述了它的职责？否 → **改名或拆分**
- [ ] 两个完全不相干的函数是否在同文件中？是 → **立即拆分**
- [ ] 修改不相关的两个需求时是否需要动同一个模块？是 → **该模块在做多件事**

**正例 vs 反例**：

```
// ❌ 反例
utils.ts           // 什么都能往里塞 → 垃圾堆
helpers.ts         // 同上
common.ts          // 同上上
class OrderManager {
  createOrder()
  cancelOrder()
  generateInvoice()   // 这是发票的事，不是订单的事
  sendEmail()         // 这是通知的事，不是订单的事
}

// ✅ 正例
dateFormatter.ts    // 只做日期格式化
apiClient.ts        // 只做 HTTP 请求
authGuard.ts        // 只做权限校验
class OrderService { createOrder(); cancelOrder() }
class InvoiceGenerator { generate() }
class EmailNotifier { send() }
```

### 戒律三：组合优于继承 (Compose, Don't Extend)

**为什么重要**：继承产生纵向耦合——父类改了，所有子类都受影响。组合产生横向独立——每个组件是独立的，替换成本低。形象地说：继承是一坨大屎山，组合是一堆小屎山。一堆小屎山永远比一个大屎山好管理。

**规则**：
- 优先使用组合（持有对象引用）而非继承（作为对象的子类）
- 继承层级不超过 2 层
- 如果子类覆写了父类大多数方法，说明继承不恰当，必须改为组合

**编码时检查**：
- [ ] 继承层级是否超过 2 层？是 → **用组合替代**
- [ ] 子类是否覆写了父类的 50% 以上方法？是 → **继承不恰当，改组合**
- [ ] 父类改动是否会级联影响多个子类？是 → **耦合过度，必须解耦**
- [ ] 能否通过 interface + 依赖注入实现同样的功能？能 → **优先用组合**

**正例 vs 反例**：

```typescript
// ❌ 反例：多层继承 + 覆写大多数方法
class Animal { walk() move() eat() }
class Bird extends Animal { fly() }
class Penguin extends Bird { fly() { throw '不会飞' } }  // 违反里氏替换

// ✅ 正例：接口 + 组合
interface IMovable { move(): void }
interface IFlyable { fly(): void }
class Penguin implements IMovable { move() { ... } }
// 企鹅不需要 fly，就不要实现 IFlyable

// ❌ 反例：用继承实现"变体"
class User { name: string }
class AdminUser extends User { permissions: string[] }

// ✅ 正例：分离角色和权限
class User { name: string }
class AdminPanel { constructor(private user: User) {} }
// 用户还是那个用户，管理员面板持有用户引用
```

### 戒律四：渐进开发，每步测试 (Build One, Verify One)

**为什么重要**：Bug 越晚发现越难修复。当屎山还小时，找 bug 和修 bug 的成本低；屎山滚大之后，一个 bug 可能牵出三个新 bug。**AI 编码尤其危险**——AI 倾向于一口气生成大量未验证的代码，这些代码局部看着合理集成后才发现耦合成一团。所以必须逐个模块来，每个模块通过测试后才能继续。

**规则**：
- 每完成一个独立模块，立即写测试验证
- 当前模块测试未通过 → **禁止开始下一个模块**
- AI 生成代码时，**一次只生成一个模块的实现**
- 测试必须覆盖边界条件（空输入、异常输入、极值）

**编码时检查**：
- [ ] 当前模块是否有测试？否 → **禁止进入下一个模块**
- [ ] 测试是否覆盖了正常路径、边界条件、异常路径？否 → **补测试**
- [ ] 当前模块的测试是否导致已有测试失败（回归）？是 → **先修复再继续**
- [ ] AI 是否在一次 prompt 中生成了多个模块的代码？是 → **AI 违规，回退逐个来**
- [ ] 测试是否验证了有意义的断言（不是"不出错就行"）？否 → **测试不合格**

**正确的 AI 编码节奏**：

```
循环直到所有模块完成：
  1. 选择下一个模块
  2. 根据接口契约用 AI 生成该模块的实现
  3. 验证实现是否符合接口契约
  4. 编写并运行该模块的测试
  5. 全部测试（含已有模块的回归测试）通过 → 进入下一个模块
  6. 有任何失败 → 修复当前模块，禁止跳过
```

### 戒律五：避免全局状态，多写纯函数 (Stateless by Default)

**为什么重要**：全局状态是耦合的隐形重灾区——它把八竿子打不着的两个模块背地里焊在一起。你改了一个全局变量，所有读这个变量的模块都可能崩溃，而你根本不知道是哪些模块。纯函数天然解耦：给什么输入就输出什么，不与外部任何东西发生交互。

**规则**：
- 纯函数 = 相同输入永远相同输出 + 无副作用 + 不依赖外部状态
- 模块间绝不允许通过全局变量共享状态
- 需要共享状态时，必须走显式的参数传递、依赖注入或消息通道
- 可变全局状态必须被封装在明确的模块内，暴露只读接口

**编码时检查**：
- [ ] 函数是否读取或修改了模块外部的变量？是 → **改为参数传递**
- [ ] 是否存在可变全局变量？是 → **能否消除或改为不可变？**
- [ ] 两个模块是否共享了一个全局状态？是 → **耦合已产生，立即消除**
- [ ] 函数调用结果是否取决于调用顺序或外部状态？是 → **不是纯函数，必须重构**
- [ ] 函数是否修改了传入的参数？是 → **不可变原则，返回新值**

**正例 vs 反例**：

```typescript
// ❌ 反例：依赖全局可变状态
let currentLanguage = 'zh'
function translate(key: string): string {
  return translations[currentLanguage][key]  // 谁改了 currentLanguage？什么时候？
}

// ✅ 正例：显式传参
function translate(key: string, language: string): string {
  return translations[language][key]
}

// ❌ 反例：函数有副作用，且结果依赖调用顺序
let counter = 0
function increment() { counter += 1; return counter }  // 每次调用结果不同

// ✅ 正例：纯函数，无副作用
function increment(value: number): number { return value + 1 }
```

## 三、AI 编码协议：先定边界，再填实现

AI 编码有一个独特的失败模式：**每一段局部看起来合理，但全局架构高度耦合。** 原因很简单：

- AI 没有跨对话的"长期记忆"——它不知道上一轮生成过哪些模块
- AI 倾向于"方便"——当前 prompt 里最直接的引用方式就是硬耦合
- AI 不会主动重构——除非你明确要求

所以，与 AI 协作编码**必须先定边界，再让 AI 钻进每个小模块里实现**。这叫"高内聚低耦合"——AI 加速的是模块内部的实现，而不是把整个系统糊成一团。

### 强制执行三步协议

#### 第 1 步：定义架构边界（人工决策，AI 可辅助讨论）

在写任何一行实现代码之前，必须明确：

1. 系统分为哪几个模块？每个模块叫什么名字？
2. 每个模块的一句话职责是什么？（戒律二的检查）
3. 模块之间的接口契约是什么？（输入参数、返回值类型、错误类型）
4. 哪些模块可以互相依赖？哪些依赖方向禁止？（禁止循环依赖）

产出：接口契约文档。使用 [assets/interface-contract.md](assets/interface-contract.md) 模板。

#### 第 2 步：逐个模块实现（AI 填充）

**绝对禁止**在一次请求中让 AI 生成多个模块的代码。

正确的做法是循环：

```
1. 取出下一个待实现的模块
2. 将模块的接口契约 + 上下文告诉 AI
3. AI 生成该模块的实现
4. 验证实现是否符合接口契约
5. 编写并运行该模块的测试
6. 测试全部通过 → 进入下一个模块
```

**如果 AI 一次生成了多个模块的代码**：拒绝该输出，拆成多次请求逐个来。

#### 第 3 步：集成验证

所有模块实现完毕后：

```
1. 将所有模块按接口契约组装
2. 运行完整集成测试
3. 验证没有产生循环依赖
4. 验证没有产生隐式全局状态耦合
5. 验证每个模块的接口契约都被正确实现
```

### AI 违规场景识别

| 违规行为 | 表现 | 纠正 |
|----------|------|------|
| 跨文件批量生成 | AI 一次输出了多个模块的代码 | 拒绝输出，拆成逐个模块的请求 |
| 跳过接口定义 | AI 直接引用实现类而非接口 | 先定义接口，再让 AI 重新生成 |
| 隐式全局耦合 | AI 使用了未在接口中声明的共享变量 | 消除变量或纳入接口契约 |
| 遗漏测试 | AI 生成的代码没有对应测试 | 补写测试，通过后才能继续 |
| 父模块膨胀 | AI 在一个模块中塞入太多职责 | 拆分子模块，每个单一职责 |
| 循环引用 | AI 让模块 A 和 B 互相依赖 | 提取共同接口或引入中间层 |

## 四、编码前自检清单

在写任何代码（或让 AI 写任何代码）之前，逐项回答以下问题。一项不明确也不要动手。

### 模块边界

- [ ] 这段代码应该放在现有哪个模块中？还是需要创建新模块？
- [ ] 如果需要新模块，它的名字和一句话职责是什么？
- [ ] 新模块的接口是什么？（输入/输出/错误类型）
- [ ] 新模块依赖哪些现有模块？这些依赖方向是否合理？

### 耦合风险

- [ ] 这个模块引入后会产生循环依赖吗？
- [ ] 这个模块需要访问全局状态吗？如果是，能改为参数传递吗？
- [ ] 修改这个模块时，是否必然需要同步修改其他模块？是 → 边界设计有问题

### AI 编码准备

- [ ] 模块边界已经确认（AI 协议第 1 步）？
- [ ] 当前要生成的模块只有一个？
- [ ] 该模块的接口契约已经书面明确？
- [ ] 该模块的测试用例已经想好？

> 完整可复用模板见 [assets/decoupling-checklist.md](assets/decoupling-checklist.md)

## 五、实现工作流

### 新功能开发

```
1. [阅读] 读取 specs/ 下需求文档和设计文档（如有）
2. [阅读] 读取 docs/ARCHITECTURE.md 了解现有模块结构（如有）
3. [自检] 执行第四章编码前自检清单
4. [定义] 明确模块边界，填写接口契约模板
5. [循环] 逐个模块：AI 实现 → 验证 → 测试 → 通过 → 下一个
6. [集成] 组装所有模块，运行回归测试
7. [记录] 更新架构文档中的模块依赖关系
```

### 重构降耦合

当发现"改一行崩三处"的模块时，按以下流程解耦：

```
1. [定位] 确定耦合最严重的模块——改它时哪些文件跟着崩？
2. [量化] 该模块被多少个模块直接依赖？它依赖多少个模块？
3. [设计] 确定要提取的接口：这个模块的哪些职责可以独立成接口？
4. [提取] 逐步提取接口，一次只重构一个耦合点
5. [验证] 每次提取后运行全部测试，确认无回归
6. [收尾] 将旧的直接依赖全部替换为接口依赖，删除旧耦合路径
```

## 六、耦合警铃：编码中的自我觉察

编码过程中，一旦注意到以下任何迹象，**立刻停下来**，你正在制造屎山：

| 警铃 | 含义 | 动作 |
|------|------|------|
| 需要打开 3+ 个文件才能理解一段逻辑 | 模块之间耦合过深 | 提取接口，切断直接依赖 |
| 犹豫"这个改动会影响哪里" | 边界不清晰，你不敢改 | 先厘清边界再做改动 |
| 在复制粘贴代码 | 缺少公共抽象 | 提取公共逻辑为独立模块 |
| 在模块 A 中写了模块 B 才能用的函数 | 职责错位 | 把函数移到它该在的模块 |
| 给函数加了第 4 个参数还在避免全局变量 | 设计需要重新思考 | 考虑引入配置对象或拆分函数 |
| 某个模块的"副作用"让其他模块行为异常 | 全局状态耦合 | 消除隐式状态共享 |
| 写完代码后不敢改它 | 屎山已经成型 | 立即重构，趁它还能改 |

## 七、触发场景

以下场景**必须调用本技能**：

| 用户输入 | 场景 |
|---------|------|
| "帮我写一个 XX 功能"、"实现 XX" | 新功能开发——从编写第一行代码前就要用本技能建立结构 |
| "用 AI 生成 XX"、"让 AI 写代码" | AI 编码场景——必须先定边界再放 AI 进入实现 |
| "重构 XX"、"优化结构"、"降低耦合"、"代码太乱了" | 主动的架构解耦 |
| "为什么每次改这里都崩"、"这里怎么这么难改" | 耦合诊断——回答"为什么难改"和"怎么解耦" |
| "设计这个系统的架构"、"模块怎么划分" | 从零开始的架构规划 |

以下场景**不触发**本技能：

| 用户输入 | 原因 |
|---------|------|
| "修这个 bug"、"这行报错了" | 局部修复，不涉及模块边界变更 |
| "这个 API 怎么用"、"这段代码什么意思" | 纯信息查询，不产生新代码 |
| `super-review` 已在执行 | 审查是事后的——执行完本技能再审查更好 |
| 已有详细 specs/design.md 且模块边界已定义 | 设计阶段完成——将本技能戒律直接应用于编码即可 |

---

## 八、与姊妹技能的协作顺序

本技能在完整开发流程中处于**编码中**位置，与已有技能形成链式协作：

```
1. development-standards   → 项目 start：确保 docs/ 规范文档就位
2. spec-driven-development → 功能 start：编写 specs/ 需求/设计/任务文档
3. decoupling-discipline   → 编码中：  每个模块按解耦戒律实现 ← 你在这里
4. super-review            → 编码 end：深度审查，兜底检查遗漏问题
```

**如果前两步被跳过**（用户直接要求编码），`decoupling-discipline` 自行承担架构定义职责：

- 从第三步开始，但第二步（架构定义）不能省略
- 在动手编码之前，花必要时间梳理模块边界和接口契约
- 宁可少写几行实现代码，也绝不能在没有边界定义的情况下开始编码
